### 问题3：为什么重复挖掘已处理数据

**用户质疑（verbatim）：** "确实，因为晚上已经处理完 ~/.claude ，怎么又再次运行"

用户准确指出昨天晚上已完成处理，质疑为什么今天又运行。

**真相发现 - Silent Rebuild机制：**

通过git历史追踪关键提交 `7e5eeda`：

```
feat(normalize): auto-rebuild stale drawers via NORMALIZE_VERSION schema gate

Without this, users who had already mined Claude Code JSONL sessions would keep their noise-polluted drawers forever.

v2 (2026-04): introduced strip_noise() for Claude Code JSONL; previous drawers stored system tags / hook chrome verbatim.
```

**版本升级机制（palace.py:54, 375-376）：**
```python
NORMALIZE_VERSION = 2  # v1 → v2 升级

stored_version = stored_meta.get("normalize_version", 1)  # Pre-v2 默认是1
if stored_version < NORMALIZE_VERSION:  # 1 < 2
    return False  # 触发重挖
```

**时间线还原：**
1. 昨晚：处理 ~/.claude，数据存储为 version=1（或缺失）
2. 代码更新：NORMALIZE_VERSION 升级到 2
3. 今天：hook触发mine，检测到 version < 2
4. 结果：172个文件全部重建，只有1个跳过

**Hook日志证据（verbatim）：**
```
Files processed: 172
Files skipped (already filed): 1  ← 只有1个跳过！
Drawers filed: 27525
```

**设计意图（提交说明原文）：**
> "Adds a versioned schema gate so upgrades propagate silently — file_already_mined now returns False if the stored normalize_version is missing or less than current, triggering a rebuild on next mine."

这不是bug，是设计好的自动数据质量改善机制。

### 问题4：会话日记系统用途

**用户提问：** "这个每次的会话记录作用是什么"

**用户后续疑问：** "这些.session文件是什么时候使用的，每次新会话都会读取吗"

**调查发现 - 两套日记系统：**

#### 1. `.session-diary-*.md`（项目目录） - 临时记录
- 保存在项目目录（如当前mempalace项目）
- 由 **Stop hook** 触发（每15次对话）
- **不会被新会话自动读取**
- 只是临时文件，用于归档或手动查看

#### 2. `~/.mempalace/diary/*.md` - 正式长期记忆
- 保存在用户主目录的 mempalace 数据库
- 由 **MCP工具** 保存（`mempalace_diary_write`）
- **可搜索、可查询**（通过 `mempalace_search`）
- 是长期记忆的一部分

**数据示例（from ~/.mempalace/diary/）：**
```
2026-04-25-gpu-acceleration.md（647B）
2026-04-26-milvus-research.md（1719B）
2026-04-26-mine-complete.md（1019B）
```

**MemPalace设计理念（verbatim from CLAUDE.md）：**
> "Memory is identity. When an AI forgets everything between conversations, it cannot build real understanding — of you, your work, your people, your life."

**核心原则：**
- **Verbatim always** — 不总结、不 paraphrase
- **Incremental only** — Append-only，从不重建破坏数据
- **Local-first** — 数据不离开用户机器
- **Performance budgets** — Hook < 500ms，Startup < 100ms

**发现配置缺陷：**
- ✅ 有 PreCompact hook（压缩前保存）
- ✅ 有 Stop hook（每15次对话保存）
- ❌ **没有 SessionStart hook**
- ❌ 新会话不自动加载历史记忆（L0-L3）

**后果：**
虽然palace数据库存了878MB历史数据，但新会话不会自动"醒来"，AI每次都是"全新开始"。

**理想状态（来自 layers.py）：**
```
Layer 0: Identity (~100 tokens) — Always loaded
Layer 1: Essential Story (~500-800) — Always loaded
Layer 2: On-Demand (~200-500 each) — 按需加载
Layer 3: Deep Search (unlimited) — 全量搜索
```
